# Модель данных и архитектура

Документ описывает итоговую схему SQLite (миграция
[bot/db/migrations/001_init.sql](../bot/db/migrations/001_init.sql)),
отличия от предварительной модели раздела 8 ТЗ и архитектуру приложения.

## 1. Схема данных

Все даты — календарные строки `YYYY-MM-DD` (Europe/Moscow), времена — `HH:MM`,
метки времени (created_at, sent_at, …) — UTC ISO-8601.

### users — клиенты
| Поле | Тип | Назначение |
|---|---|---|
| id | INTEGER PK | |
| telegram_id | INTEGER UNIQUE | идентификация клиента (A.1.5) |
| username | TEXT | обновляется при входе |
| name, phone | TEXT | фиксируются при оформлении записи |
| created_at | TEXT | |

### admins — whitelist администраторов
| Поле | Тип | Назначение |
|---|---|---|
| user_id | INTEGER PK → users | |
| is_primary | INTEGER | ровно один основной (гарантируется ensure_primary) |
| added_by, added_at | | кто и когда добавил второго |

### schedule_templates — недельный шаблон
`weekday` (0=пн…6=вс, PK), `is_working_day`, `start_time`, `end_time`.
Отсутствие строки = выходной.

### schedule_exceptions — исключения на дату
`date` (PK, ISO), `is_working_day`, `start_time`, `end_time`, `note`
(«выходной», «рабочий день отменён», …). Сильнее шаблона.

### blocked_slots — ручные блокировки
`date`, `slot_start`, `slot_end`, `reason`; `UNIQUE(date, slot_start)`.
Только существующие слоты сетки дня.

### categories / services — справочник услуг
Категории: «Стрижка», «Борода и усы» (предзаполнены). Услуга:
`category_id`, `name`, `description`, `price` (целые рубли), `is_active`
(soft delete), `sort_order`.

### bookings — записи
| Поле | Тип | Назначение |
|---|---|---|
| client_id | FK users, NULL | NULL у ручной записи без совпадения по телефону |
| client_name, client_phone | TEXT | **снимки на момент записи** — работают и для ручных записей, и для анонимизации со сохранением статистики |
| created_by | TEXT | 'client' / 'admin' — управляет мгновенными уведомлениями (п. 4.5 ТЗ) |
| status | TEXT | 'active' / 'cancelled'; прошедшие вычисляются на лету (допущение № 6 плана) |
| total_price | INTEGER | сумма цен на момент записи |
| pd_consent_at | TEXT | согласие 152-ФЗ при оформлении (NULL у ручных) |
| is_anonymized | INTEGER | флаг идемпотентности анонимизации |
| cancelled_at, cancel_reason, cancel_initiator | | инициатор: client / admin / auto_day / auto_blocked |

### booking_slots — слот записи
`booking_id`, `date`, `slot_start`, `slot_end`, `is_active`.
**Частичный уникальный индекс** `ux_active_slot (date, slot_start) WHERE
is_active = 1` — вторая линия защиты от двойного бронирования (п. 6.2 ТЗ);
отмена записи снимает слот (`is_active = 0`).

### booking_services — состав записи
`name_at_booking`, `price_at_booking` — снимки: изменение прайса и скрытие
услуги не затрагивают существующие записи (A.3.5).

### notifications — план и история уведомлений
`booking_id` (NULL у служебных), `type` (`client_24h`, `client_2h`,
`admin_1h`), `recipient_tg_id` (0 = все админы, NULL = пропущено),
`planned_at`, `status` (`pending → sending → sent/failed/skipped`),
`sent_at`, `error`. **`UNIQUE(booking_id, type)`** — идемпотентность
напоминаний (п. 9.1 ТЗ). Индекс `(status, planned_at)` для выборки due.

## 2. Отличия от предварительной модели ТЗ (раздел 8)

| ТЗ (предварительно) | Реализация | Причина |
|---|---|---|
| users.role | нет поля | роль определяется только таблицей admins — один источник правды |
| bookings: client_id | client_id + снимки client_name/client_phone | ручные записи без Telegram-аккаунта; анонимизация без потери статистики |
| — | bookings.pd_consent_at | фиксация согласия 152-ФЗ (п. 9.2 ТЗ) |
| — | bookings.is_anonymized | идемпотентность ежемесячной задачи |
| booking_slots: уникальный индекс по активным | частичный индекс WHERE is_active = 1 | отмена не удаляет строку, индекс следит только за активными |
| notifications_log | notifications + planned_at + статусная модель | одна таблица обслуживает план и историю; идемпотентность |
| status 'completed' | не хранится | прошедшие записи вычисляются на лету по дате/времени слота |

## 3. Архитектура

```
              ┌────────────────────────── один процесс ──────────────────────────┐
 Telegram ───▶ │ polling (aiogram Dispatcher)                                     │
              │   middlewares: регистрация пользователя → сессия БД               │
              │   фильтры ролей (IsAdmin / IsPrimaryAdmin)                        │
              │   handlers: client/… admin/…  ──▶  services (домен)               │
              │                                       │                            │
              │   repositories (весь SQL, абстракция под PostgreSQL) ◀────────────┤
              │                                       │                            │
              │ APScheduler: напоминания (1 мин), анонимизация (03:00),            │
              │              бэкап (15 мин)          ▼                              │
              │                                SQLite (WAL, BEGIN IMMEDIATE + Lock)│
              │ health-сервер aiohttp :PORT/health ◀── keep-alive пинг (внешний)   │
              └───────────────────────────────────────────────────────────────────┘
```

Принципы (план разработки, раздел 1.2):

1. **Один асинхронный процесс** — упрощает PaaS-развёртывание.
2. **Домен отделён от Telegram** — `services/scheduling.py` — чистые функции,
   тестируются без бота.
3. **Истина состояния — в базе**: записи и планы напоминаний переживают
   рестарты; диспетчер идемпотентен, `reconcile` при старте досоздаёт
   недостающие планы и гасит лишние.
4. **Транзакции сериализованы** процессным asyncio.Lock + `BEGIN IMMEDIATE`:
   параллельные бронирования обрабатываются последовательно (B.4), частичный
   уникальный индекс — страховка на уровне СУБД.
5. **Единый отправитель** — все сообщения идут через `Notificator`
   (blocked / 429 / ошибки API не роняют бота), реакция на блокировку —
   автоотмена записи в сервисе отмены.
6. **Абстракция под PostgreSQL**: SQL живёт только в `db/repositories/`,
   типы данных и синтаксис запросов выбраны совместимыми; миграции —
   нумерованные SQL-файлы.

## 4. Жизненный цикл записи

```
выбор услуг → дата → слот → имя → телефон → согласие (152-ФЗ)
   → ТРАНЗАКЦИЯ: проверка дня и слота → bookings + slots + services + планы
   → мгновенные уведомления (только если создал клиент)
   → напоминания 24/2 ч клиенту и 1 ч админам (планировщик)
   → отмена (клиент ≥4 ч / админ / авто) → слот свободен, планы погашены
   → через 2 месяца после визита: анонимизация ПД, статистика остаётся
```
