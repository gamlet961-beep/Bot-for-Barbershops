# Фаза 3 — Редактор расписания и сервис записей

> Отчёт по плану разработки (разделы 5.4–5.5). Статус: **завершена** 21.11.2026.

## Что сделано

### Ядро транзакций (сервис записей)

- **`bot/services/booking.py`** — `BookingService`:
  - `create_booking` — единая транзакция BEGIN IMMEDIATE: проверка рабочего
    дня → проверка свободности слота → вставка bookings + booking_slots +
    booking_services (снимки названий/цен) + планы напоминаний. Исключения:
    `SlotTakenError` (UC-7), `DayOffError`;
  - `cancel_booking` — единая точка отмены для любого инициатора
    (client / admin / auto_day / auto_blocked): статус cancelled, слот
    освобождается, планы напоминаний гаснут, уведомления по матрице ТЗ;
  - `cancel_working_day` — исключение «день отменён» + автоотмена всех
    активных записей дня + уведомления клиентам «рабочий день отменён» +
    отчёт админам (UC-8).
  - Мгновенные уведомления отправляются строго ПОСЛЕ коммита; при создании
    записи админом вручную — не отправляются (п. 4.5 ТЗ).
- **Репозитории**: `schedule.py` (шаблоны, исключения, блокировки, каскадный
  резолв дня), `bookings.py` (вставка, активные слоты, представления, отмена),
  `notifications.py` (планы 24 ч / 2 ч / 1 ч, статусная машина pending →
  sending → sent/failed/skipped, `UNIQUE (booking_id, type)`).
- **Шаблоны сообщений** `bot/utils/formatting.py` — дословные тексты ТЗ:
  подтверждение (п. 5.6), «Клиент … отменил запись …», «Через час клиент …
  записан …», «Запись отменена, клиент заблокировал бота», предупреждение
  об удалении дня (п. 4.2). Все пользовательские данные экранируются (HTML).
- **Отправитель** `bot/services/notifications.py` — единая точка отправки:
  обработка blocked/429/ошибок API без падения (B.6), рассылка всем админам;
  в тестах подменяется записывающим.

### Интерфейс администратора

`bot/handlers/admin/schedule.py` — редактор расписания (п. 4.2 ТЗ):

- **Шаблон недели**: обзор всех 7 дней с текущим состоянием, выбор дня,
  задание рабочих часов или пометка выходным;
- **Исключения на дату**: список будущих, добавить (изменить часы /
  выходной-отпуск), удалить (возврат к шаблону);
- **Блокировка слотов**: сетка дня с пометками (занят записью ✖ /
  заблокирован 🔒 / свободен ◻), блокировка только существующих слотов,
  разблокировка по датам и слотам;
- **Отмена рабочего дня**: при отсутствии записей — сразу; при наличии —
  предупреждение дословно по ТЗ с кнопками Да/Нет; «Нет» ничего не меняет.

## Результат фазы

Админ может полностью управлять расписанием; создание и отмена записей
гарантированно согласованы на уровне БД. Кнопка «Расписание» в меню админа
открывает редактор (заглушка фазы 1 снята).

## Тесты

```
57 passed in 0.15s (+10 новых: test_booking.py)
```

Покрытие: снимки цен и планов при создании, бронь в нерабочий день,
последовательное и **параллельное** бронирование одного слота (побеждает
одна, вторая — SlotTakenError; в таблице слотов одна строка), блокировка
слота, отмена (слот свободен, планы погашены, админам «отменил запись»),
отмена админом (клиент уведомлён), ручная запись без мгновенных уведомлений
и с напоминанием админу за 1 ч, ручная запись с привязкой клиента по телефону
(планы клиенту 24/2 ч — п. 7.1 ТЗ), полное течение отмены рабочего дня.

**Найден и исправлен критичный дефект:** конкурентные транзакции в одном
event loop давали «cannot start a transaction within a transaction».
Транзакции сериализованы процессным asyncio.Lock (Database.transaction) —
это и есть требование B.4 акта «параллельные запросы обрабатываются
последовательно». Дефект поймал тест `test_parallel_booking_only_one_wins`.

## Зафиксированные решения

1. Транзакции сериализуются процессным Lock — вложенных транзакций в коде
   нет (все мутации идут через сервис или собственную транзакцию репозитория).
2. Ручная запись связывается с клиентом по телефону (UsersRepo.get_by_phone):
   тогда напоминания клиенту 24/2 ч планируются штатно (п. 7.1 ТЗ); без
   совпадения клиентские планы создаются сразу «skipped» — факт виден в БД.
3. Отчёт при отмене дня уходит всем админам через Notificator (как и требуют
   «Админ(ы)» в ТЗ), а не только нажавшему.
