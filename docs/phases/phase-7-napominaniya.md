# Фаза 7 — Планировщик напоминаний

> Отчёт по плану разработки (раздел 5.9). Статус: **завершена** 21.11.2026.

## Что сделано

- **`bot/services/reminders.py`** — `ReminderService`:
  - **диспетчер** `dispatch_due` (вызов раз в минуту из APScheduler): выбор
    наступивших планов, атомарный claim `pending → sending` (повторная выдача
    исключена), отправка (admin_1h — всем админам; клиентские — получателю),
    фиксация `sent` / `failed`; если запись успели отменить — план гасится
    в `skipped`;
  - **блокировка бота** (п. 7.3 ТЗ): ошибка доставки клиентского напоминания →
    автоотмена записи (initiator=auto_blocked), освобождение слота, уведомление
    админам «Запись отменена, клиент заблокировал бота» с деталями;
  - **восстановление** `reconcile` при старте процесса: застрявшие `sending`
    помечаются отправленными без подтверждения (семантика «не более одного
    раза» — дубли исключены), недостающие планы у активных будущих записей
    досоздаются (INSERT OR IGNORE по UNIQUE booking_id+type), планы
    отменённых записей гасятся.
- **main.py**: APScheduler (AsyncIOScheduler, таймзона Europe/Moscow):
  `reconcile()` при старте + job диспетчера каждые 60 секунд
  (max_instances=1, coalesce — защита от наложения), корректная остановка
  планировщика при завершении.
- Репозиторий notifications дополнен: `mark_skipped`, колонка `error`
  в выборке планов.

## Результат фазы

Полный контур отложенных уведомлений: планирование при создании записи,
диспетчеризация, идемпотентность, восстановление после рестарта, автоотмена
при блокировке бота. Мгновенные уведомления работали с фазы 3.

Покрытие: напоминание админу за 1 час по ручной записи — обоим админам,
дословный текст; клиентские напоминания за 24 ч и за 2 ч; идемпотентность
повторного прогона (A.7.9); отменённая запись не порождает отправок;
**автоотмена при блокировке бота** — статус cancelled, инициатор auto_blocked,
слот освобождён, админы уведомлены, остальные клиентские планы погашены
(A.7.8, UC-9); восстановление утраченных планов без дублей (B.2); застрявшие
sending → sent(unconfirmed); сценарий «рестарт между отправкой и фиксацией» —
дубля нет.

**Найден и исправлен дизайн-дефект:** ручная запись без совпадения по телефону
теряла имя и телефон клиента (client=None → снимки не сохранялись). Теперь
manual-обработчик всегда передаёт снимки имени/телефона, а привязка к
аккаунту делается только при совпадении. Поймано расхождением текста
напоминания в тесте.

## Зафиксированные решения

1. Статусная машина `pending → sending → sent/failed/skipped`: claim выполняется
   атомарным UPDATE по условию — повторный запуск диспетчера безопасен.
2. Выбрана семантика «не более одного раза»: строка, застрявшая в sending
   при падении процесса, помечается отправленной (одно напоминание может
   потеряться в узком окне сбоя, дубли исключены — требование п. 9.1 ТЗ).
3. Один план admin_1h на запись (получатель «Админ(ы)»), fanout по текущему
   списку админов в момент отправки.
